# 改动与配置

用于用户当前要求实现功能、修改行为或修正工程配置时。根据当前要求、相关实现和已有检查，交付指定的行为变化与对应检查结果；不因文件中出现代码而启动本方法。

## 确定需要改变的行为

结合用户目标、现有实现和实际使用场景，确定需要改变的输入、行为或结果。先查看能回答重要问题的代码、调用方、配置和现有材料；仅对无法查明且会改变结果的信息询问。已有授权覆盖的可逆工作直接完成。

简单明确的任务直接修改。例如只改一处界面文案时，查看该文案及相关显示位置，完成修改并执行项目对此类改动要求的检查；不另建规格文档或与文案无关的测试。只有需求存在会改变实现的分歧时才澄清，不自动增加设计审批或固定清单。

## 结合现有实现完成改动

遵循项目已有结构和约定，处理本次行为涉及的调用路径与接口。保留用户已有改动；遇到同一文件的并行修改时检查相关内容后继续，无法确定归属且会造成覆盖时再澄清。

只增加有具体用途的代码或资源。新抽象、依赖、文档、脚本和代理协作需要解决明确需求、已观察问题或可说明的失败机制；不顺带重构无关部分。

配置修改要核对作用范围、实际加载位置及生效条件，检查需要重启、重新构建还是重新加载。保留既有敏感值，不在输出中展示其内容。涉及发布或生产数据迁移时，按需要追加相应参考。

## 检查用户关心的结果

保留项目必要检查，并按本次行为和可信的回归风险选择验证范围。新增测试应检查用户可观察的结果或真实接口约束，不按函数数量、固定顺序或全套运行次数安排。

计算改动核对具体输入与预期结果；界面改动观察相关交互；配置改动确认目标应用确实读取并应用相应值。编译、格式或命令退出成功只说明其各自检查范围。

任务明确要求逐字输出或保留原有文件字节、编码、换行时，核对实际交付文件或 stdout 的原始字节；文本模式可能将 CRLF 归一化为 LF，文本比较通过不能据此证明字节相同。没有这类要求时，不扩大为逐字节验证。

已经获得且状态未变的结果可以复用；修改、失败、环境变化或未解决问题才触发相关复验。交付说明改变了什么、为何需要改变、检查得到的结果和仍未确认的限制，不把拟执行的动作写成已经完成。
